# ADR 0014 — Control plane + storage as config source of truth

- Status: Accepted
- Date: 2026-07-03
- Deciders: project owner
- Spec refs: I.cp, I.store, V25, V30, V34

## Context

The fleet must check somewhere between five thousand and fifty thousand-plus
endpoints, authored by many different teams across many different projects.
At that scale, config cannot live in local TOML files scattered across
workers — there needs to be a single, central source of truth that a
Terraform provider can write to and that every worker in the fleet can read
from. The system also needs a clean boundary between the path that writes
config and the path that consumes it, so that authoring, validation, and
authorization can happen in one place while workers stay simple consumers.

A related question is what else, besides config, should live in that central
store. Check results are the obvious candidate, since they are generated by
the same fleet and need to go somewhere — but conflating results storage with
config storage would turn a small, simple database into a time-series store
carrying a very different scale and access pattern.

## Decision

A control-plane (CP) service, written in Rust, is the authority for fleet
config. It persists both the config hierarchy and fleet membership behind a
`ConfigStore` trait (ADR 0020), rather than embedding a specific database
directly into its logic. The CP resolves hierarchy inheritance server-side
(ADR 0017), so what it serves to workers is always a flat, fully-materialized
list of checks — workers never see or resolve the hierarchy themselves.

Critically, the store behind the CP holds config and worker heartbeats
**only**. It never holds check results or time-series data. Results flow from
the worker, through the DogStatsD sink (ADR 0005), to Datadog. This keeps the
CP's database small, fast, and cheap to operate, and avoids building and
maintaining a second time-series database that duplicates what Datadog
already provides.

## Consequences

- There is a single authority for config, with one write path (Terraform
  through the CP) and one read path (workers reading from the CP), instead
  of config drifting across ad hoc files.
- The CP's database stays small and simple because it never accumulates
  result data — it only ever holds the current config and current fleet
  state.
- The CP becomes a new, critical operational component that has to be run,
  monitored, and kept available. Workers are designed to tolerate its
  outages gracefully (ADR 0016, ADR 0019) rather than fail outright, but it
  is still one more service in the system's operational surface.

## Alternatives considered

- **Terraform writes directly to the database** — rejected; this removes any
  validation or authorization boundary between an apply and the fleet's live
  config.
- **A rendered config bundle in object storage** — rejected; a static bundle
  has no way to express per-worker assignment or live fleet membership.
- **Storing check results in the CP's database** — rejected; this turns the
  database into a time-series store at fleet scale, duplicating Datadog for
  no benefit.
